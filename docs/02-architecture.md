# 2. 전체 구조

## 식당으로 이해하기

| 식당 | 이 프로젝트 | 하는 일 |
|---|---|---|
| 손님 | 사용자 (웹 브라우저) | 주문(요청)을 한다 |
| 출입문 경비 | **공통 규칙** (`server/web.py`) | 이상한 손님을 걸러내고, 문제가 생기면 같은 모양의 안내문을 준다 |
| 메뉴별 담당자 | **기능 파일** (`server/features/*.py`) | 주문 접수 → 처리 규칙 → 창고 출납까지 자기 메뉴는 혼자 끝까지 맡는다 |
| 창고 | **MySQL** (PC에 이미 떠 있는 컨테이너) | 저장된 모든 자료 |
| 레시피북 | **계산 엔진** (`server/domain`) | 사업성 계산법, 정부 자료 가져오는 법. 손님·창고는 모른다 |
| 외부 식자재 업체 | **공공 API** (브이월드 등) | 필지·실거래 정보를 공급 |
| 새로 온 요리사 | **학습 모델** (`server/features/model.py` + `data/models/land_price_linear.py`) | 토지 그룹의 6개월 뒤 단가를 예측 (선형회귀. 예전 CatBoost 23번은 `land_price_model.py`). 이 금액이 '예상 토지매입대금'이 됨 |

### 왜 이렇게 나눴나요?

**"한 기능은 한 파일에서 끝까지 읽히게"** 하기 위해서입니다. 예를 들어 "분석 저장"이 궁금하면 `features/snapshots.py` 하나만 열면 됩니다. 파일 안은 위에서부터 **URL(라우터) → 업무 규칙 → DB 읽기/쓰기** 순서입니다. Spring으로 치면 Controller·Service·Repository가 한 파일에 차례로 들어 있는 모양입니다.

여러 기능이 같이 쓰는 것만 따로 뺐습니다.

- `web.py`: 오류 응답 모양, 요청 본문 검사, 접속 주소 검사, 인증키 유출 차단
- `db.py`: 테이블 정의와 MySQL 연결
- `domain/`: 계산 엔진 (웹·DB를 모름)

 │       ▼                                                     │
 │ server/features/    기능별 파일 (URL → 업무 규칙 → DB)        │

## 폴더 지도

처음 열었을 때 **이것만 보면** 됩니다. 파일 하나하나의 설명은 [server/README.md](../server/README.md)에 있습니다.

```
프로젝트/
├─ docker-compose.yml   ← api 컨테이너 하나를 켜는 설명서 (MySQL은 새로 띄우지 않음)
├─ Dockerfile           ← api 프로그램을 포장하는 방법
├─ .env.example         ← 비밀번호·키를 적는 양식 (복사해서 .env로 사용)
│
├─ server/              ← ★ 서버 (파이썬 코드는 전부 여기)
│   ├─ main.py          │  조립: 설정 → MySQL 연결 → 기능 객체 → URL 등록
│   ├─ settings.py      │  .env → 설정값
│   ├─ env.py           │  .env 파일 읽기 · 키 형식 검사
│   ├─ web.py           │  공통 규칙 (아래 '안전장치')
│   ├─ db.py            │  테이블 정의 · 연결
│   ├─ features/        │  메뉴별 담당자: 기능별 파일
│   │   ├─ pages.py           대시보드 화면
│   │   ├─ system.py          상태 확인
│   │   ├─ public_data.py     공공 API 조회
│   │   ├─ snapshots.py       사업성 계산 · 분석 저장
│   │   ├─ portfolio.py       샘플 선반
│   │   ├─ model.py           학습 모델 자리
│   │   └─ land_store_mysql.py 토지 실거래 캐시 저장소
│   └─ domain/          │  레시피북: 웹·DB를 모르는 계산 코드
│       ├─ analysis/          사업성 계산 (계산 단계별 파일: 개발 규모 → 분양 수입 → 토지비 → … → 현금흐름)
│       ├─ public_api.py      정부 공공 API에 묻는 창구
│       ├─ survey.py          입지 조사
│       └─ land.py, boundary.py, regions.py …  토지 분류·경계 배분·지역 목록
│
├─ frontend/build/      ← 화면 HTML 파일 하나 (V6.template.html, 스크립트·스타일 포함)
├─ data/                ← 코드가 아닌 자료
│   ├─ samples/         │  기본으로 들어 있는 예시 분석 (안산 장상동 27필지)
│   └─ models/          │  학습 모델 (land_price_linear.py + linear/model.joblib, 예전 CatBoost)
├─ tests/               ← 자동 점검 (계산이 맞는지, 안전장치가 작동하는지)
└─ docs/                ← 지금 읽는 문서
```

### 계산 엔진은 이렇게 나뉘어 있습니다

수지분석 한 번은 아래 순서로 계산합니다. 단계마다 파일이 하나씩 있어서, 예를 들어 공사비가 궁금하면 `costs.py`만 열면 됩니다.

| 순서 | 계산 | 파일 (`server/domain/analysis/`) |
|---|---|---|
| ① | 개발 규모: 지을 수 있는 면적·세대수 | `development.py` |
| ② | 분양 수입: 주변 분양사례 단가 × 면적 | `revenue.py` |
| ③ | 토지 매입가: 주변 토지 실거래 사례 | `land_price.py` |
| ④ | 금융 단가·예산 배분 | `costs.py` |
| ⑤ | 현금흐름: 월별 수입·지출 | `cashflow.py` |
| ⑥ | 사업비 합계 (금융비가 현금흐름에 달려 있어서 ⑤ 다음) | `costs.py` |
| ⑦ | 목표 지표 | `engine.py` |

전체 순서는 `engine.py`의 `analyze()`가 지휘하고, ②③이 함께 쓰는 "비교사례 고르는 규칙"은 `comparables.py`, 모두가 쓰는 숫자·날짜 검사는 `common.py`에 있습니다.

## 안전장치 (`server/web.py`)

모든 요청에 공통으로 적용됩니다.

| 장치 | 하는 일 |
|---|---|
| 주소 검문 | 허용된 주소로 들어온 요청만 받는다. 다른 사이트에서 몰래 보낸 요청은 거절 |
| 열쇠 차단 | 응답에 API 키나 DB 비밀번호가 섞여 있으면 **보내지 않고 막는다** |
| 크기 제한 | 요청이 64MB를 넘으면 거절 |
| 오류 통일 | 무슨 문제가 생겨도 같은 모양의 안내문으로 답한다. 내부 정보는 노출하지 않는다 |
| 동시 조회 제한 | 정부 사이트 조회는 동시에 4건까지. 초과하면 "잠시 후 다시" 안내 |

## 데이터베이스에 저장되는 것

| 저장 대상 | 설명 |
|---|---|
| 분석 저장본 | 사용자가 "저장"을 누른 분석 결과 |
| 샘플 선반 | 보관용으로 고정해 둔 분석. 한번 저장하면 바뀌지 않음 |
| 기본 샘플 설정 | 화면을 열 때 처음 보여줄 샘플이 무엇인지 |
| 토지 실거래 | 직접 쌓아 둔 `land_trade` 테이블에서 읽습니다 (화면 조회 때 정부 사이트에 묻지 않음). 매일 새벽 3시에 서버가 최근 3개월을 다시 받아 갱신합니다. 예전 방식(`LAND_TRADE_SOURCE=api`)으로 바꾸면 정부 사이트에서 받아 앱 캐시 테이블에 보관합니다 |
| 청약홈 분양정보 | 직접 쌓아 둔 `applyhome_apt_notice`·`applyhome_apt_model` 테이블에서 읽습니다. 매일 새벽 3시에 서버가 전체를 다시 받아 갱신합니다 (`APPLYHOME_SOURCE=api`로 바꾸면 정부 사이트에 조회) |

데이터는 기존 MySQL 컨테이너에 보관되어서 api를 껐다 켜거나 다시 빌드해도 남습니다.

## Docker란?

프로그램과 실행에 필요한 모든 것을 **하나의 상자(컨테이너)** 에 담아 두는 기술입니다. "내 컴퓨터에선 되는데 네 컴퓨터에선 안 돼요"를 막아 줍니다.

- **MySQL 상자:** PC에 이미 떠 있는 것을 그대로 씁니다. 이 프로젝트가 새로 만들거나 지우지 않습니다.
- **api 상자:** 이 서버 프로그램. `docker compose up -d --build`로 켭니다. Docker 없이 `python -m server`으로 켜도 됩니다.

api 상자와 MySQL 상자(`land-mysql`)를 같은 네트워크(`v6_mysql`)에 묶어 두면, api는 `land-mysql`라는 이름만으로 MySQL을 찾아갑니다 (`docker-compose.yml`에 설정됨).
