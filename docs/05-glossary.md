# 5. 용어집과 앞으로의 계획

## 용어집

| 용어 | 쉬운 설명 |
|---|---|
| **필지** | 지번이 붙은 땅 한 덩어리 |
| **사업성 / 수지분석** | 개발해서 팔았을 때 수입과 비용을 비교해 이익이 남는지 따지는 것 |
| **PNU** | 필지마다 붙은 19자리 고유번호 (주민번호 같은 것) |
| **공공 API** | 정부 사이트가 프로그램에게 자료를 주는 창구 |
| **API 키** | 그 창구를 이용할 권한을 증명하는 비밀번호 |
| **서버 / 백엔드** | 화면 뒤에서 계산하고 저장하는 프로그램 |
| **프런트엔드** | 사용자가 눈으로 보는 화면 |
| **FastAPI** | 서버를 만드는 Python 도구. 이 프로젝트의 "홀 직원" 틀 |
| **MySQL** | 데이터를 표(테이블) 형태로 보관하는 데이터베이스 |
| **Docker / 컨테이너** | 프로그램을 필요한 모든 것과 함께 담은 상자 |
| **docker-compose** | 여러 상자를 한 번에 켜는 설명서 |
| **계층** | 역할별로 나눈 층. 위층만 아래층을 부른다 |
| **캐시** | 같은 자료를 다시 받지 않도록 임시 보관해 둔 것 |
| **스냅샷 / 저장본** | 특정 시점의 분석 결과를 그대로 저장한 것 |
| **샘플 선반(포트폴리오)** | 바뀌지 않게 고정해 둔 대표 분석 모음 |
| **환경변수 / .env** | 비밀번호·키처럼 코드에 적으면 안 되는 설정을 따로 적는 파일 |
| **학습 모델** | 과거 자료로 학습시켜 값을 예측하는 AI 프로그램 |
| **엔드포인트** | 서버가 받는 요청 종류 하나 (예: 저장, 조회) |

## 앞으로의 계획: 학습 모델 추가

모델은 아직 없지만, **들어올 자리와 규격**이 이미 있습니다.

### 현재 준비된 것

- `data/models/` 폴더: 모델 파일을 넣을 곳 (컨테이너에는 읽기 전용으로 연결)
- `server/features/model.py`: "모델은 이런 모양이어야 한다"는 규격(`Predictor`)
  - 이름(`name`), 버전(`version`)을 가진다
  - `load`: 시작할 때 파일을 불러온다
  - `predict`: 입력값을 받아 예측 결과를 돌려준다
- `/api/model/status`, `/api/model/predict`: 모델 상태 확인 / 예측 요청 창구

### 모델이 준비되면 할 일

1. 모델 개발자가 위 규격에 맞는 파일 하나를 `data/models/`에 넣는다 (예시: [data/models/README.md](../data/models/README.md))
2. `.env`에 `MODEL_ENTRYPOINT=파일이름:클래스이름` 한 줄을 추가한다
3. `docker compose up -d --build api` 로 다시 켠다
4. `/api/model/status`가 `ready`로 바뀌면 사용 가능

### 알아둘 점

- 모델을 넣다 **실패해도 서버는 정상적으로 켜집니다.** 예측 기능만 "실패" 상태로 표시됩니다.
- 기존 사업성 계산 엔진은 **모델과 무관**합니다. 모델 결과를 계산에 반영하려면 `server/features/`에 연결 코드를 새로 추가해야 하며, 이는 별도 작업입니다.
- 모델이 필요로 하는 추가 라이브러리(예: scikit-learn)는 `requirements.txt`에 넣고 이미지를 다시 빌드해야 합니다.
- 모델 파일은 실행 코드를 포함할 수 있으므로 **신뢰할 수 있는 곳에서 만든 것만** 넣습니다.

## 알려진 한계

- 데이터베이스 테이블은 시작할 때 자동 생성됩니다. 나중에 테이블 구조를 바꾸게 되면 별도의 변경 절차(마이그레이션)를 도입해야 합니다.
- 예전 방식(파일)으로 저장했던 분석과 토지 거래 캐시는 데이터베이스로 자동 이전되지 않습니다.
- 여러 사용자가 동시에 쓰는 서비스용 인증(로그인)은 없습니다. 한 팀이 내부에서 쓰는 전제입니다.
