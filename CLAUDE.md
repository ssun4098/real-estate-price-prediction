# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

개발사업성 분석 V6: a real-estate development feasibility tool. A prebuilt React dashboard (`frontend/build/V6.template.html`) talks to a Python backend that calls Korean public APIs (VWorld, data.go.kr, Juso, KOSIS, SGIS) and runs the financial analysis engine. UI text, errors and comments are mostly Korean; keep that.

## Running

There is one server: the FastAPI app, the `server/` package (the old stdlib server `V6.py`/`pf_server.py` was removed). All Python lives in `server/`; `server/domain/` is the calculation/public-API layer.

## Architecture of `server/`

`server/README.md` is the human-facing code map (Spring analogies, how to add a feature); keep it in sync when files move.

Organised **by feature**, so one feature reads top to bottom in one file. The user found the previous strict layering (api/services/repositories/db/core/container, ~35 files) too hard to follow; don't reintroduce per-layer packages.

- `main.py` — `create_app()`: lifespan builds everything (DB → `Collector` + land store (`LandTradeTable` or `MySqlLandStore`) → feature objects) and stores it on `app.state`; registers the `guard` middleware and the routers. Run with `uvicorn server.main:create_app --factory` (no module-level `app`).
- `settings.py` — `Settings.from_env()`. `env.py` — `.env` loader and API-key validation. `web.py` — shared HTTP rules. `db.py` — ORM tables, `connect()`, `db_errors()`.
- `features/<name>.py` — each file: routes at the top (`router = APIRouter()`), then the rules/DB code (`SnapshotService`, `PortfolioService`, `PublicData`, `ModelHolder`). Routes reach their object via `request.app.state.<name>`. A new feature = a new file here + one line in `main.py`.
- Imports are absolute from the project root (`from server.domain.analysis import analyze`); there is no `sys.path` manipulation. Dependency direction is one way: `features → domain`; `domain` never imports `features`, FastAPI or SQLAlchemy.
- Errors: the `guard` middleware in `main.py` catches every exception and returns `web.error_response(exc)` → `{"error":{"code","message"}}` (`ValueError/KeyError/TypeError` → 400, `ApiError` keeps its status, other → 500 with a generic message, nothing logged). FastAPI's own 404/405/validation errors are mapped by registered exception handlers. Handlers return `ok(data)` (`SafeJSONResponse`), not dicts, to avoid re-serialising up-to-64MB documents; every response body is refused if it contains a configured API key or the DB password.
- Request bodies are parsed by the `json_body` dependency (JSON content type, 64MB cap, NaN rejected). There is no Host allow-list (the user removed `ALLOWED_HOSTS` on purpose; don't reintroduce it). `check_origin` only rejects cross-site requests: `Sec-Fetch-Site: cross-site`, or an Origin that is not `http://`/`https://` + the request's own Host.
- Access logging is disabled on purpose (URLs carry addresses and upstream keys).

### Storage

The app does **not** run its own MySQL: it connects to a MySQL 8.4 container the user already runs on their PC (it also holds their own land-trade data). In Docker the api joins the external network `v6_mysql` (`MYSQL_NETWORK`) and reaches the container by name (`MYSQL_CONTAINER`, default `land-mysql`) on port 3306; the user connects it once with `docker network connect v6_mysql land-mysql`. Directly (`python -m server`), via `MYSQL_HOST`/`MYSQL_PORT`. `db.connect` only creates missing app tables, never alters/drops existing ones, and refuses to start if a same-named table lacks expected columns. Never add code that drops, truncates or migrates tables it did not create.

Land trades: by default (`LAND_TRADE_SOURCE=table`) `Collector` reads the user's own bulk-loaded tables via `features/land_trade_table.LandTradeTable` (set as `collector.land_store` with `collector.land_source="table"`): `land_trade` (one row per deal, `lawd_cd`+`deal_ym`) and `land_trade_job` (a month counts only if `loaded_rows >= total_count`; missing months raise `LAND_NOT_LOADED`, never treated as zero). No public-API call is made for land in this mode. Row verdicts reuse `public_api.land_trade_row()` so DB and API paths judge identically; row ids mimic API paging (100/page). Request handling only reads these tables; the only writer is the daily loader. A daily loader (`features/daily_load.DailyLoader`, started in `main.py` lifespan as a daemon thread; `DAILY_LOAD=on|off`, `DAILY_LOAD_TIME=HH:MM` KST, `DAILY_LOAD_MONTHS`) refreshes these tables: last N completed months × sgg codes found in `land_trade_job` (DELETE+INSERT per month, `REPLACE` job row, failures to `land_trade_fail`), then full Applyhome notices/models via `REPLACE` (failures to `applyhome_fail`). It mirrors the user's original loaders (`land_trade.py`/`applyhome.py` in their separate land_trade folder), calls the API through `Collector.request` (not `odcloud`/`_land_page`, which are diverted to the tables), stops on auth/quota errors, redacts secrets in stored errors, and takes a MySQL `GET_LOCK`. Status `GET /api/daily-load`, manual `POST /api/daily-load/run`. `LAND_TRADE_SOURCE=api` restores the old API + `MySqlLandStore` cache path.

Indexes for the user's own tables are NOT created by the app (it must not migrate tables it didn't create); the user runs `deploy/mysql-indexes.sql` by hand. It adds only missing indexes (skips when an existing index/PK starts with the same columns, skips missing tables, online `ALGORITHM=INPLACE, LOCK=NONE`): `land_trade(lawd_cd, deal_ym)` (the critical one — comparables read 60 sgg-months per lookup; without it each month full-scans ~7.6M rows: measured 3.7 s/month → 6 ms), `land_trade_job`/`land_trade_fail(lawd_cd, deal_ym)`, `applyhome_apt_notice(house_secd, house_dtl_secd, rcrit_pblanc_de)`, `applyhome_apt_model(house_manage_no, pblanc_no)`. If you add a query on these tables, update that script.

청약홈 (Applyhome) notices/models: by default (`APPLYHOME_SOURCE=table`) `collector.applyhome_table = ApplyhomeTable(sessions)` (`features/applyhome_table.py`), and `Collector.odcloud()` / `_coverage_count()` query `applyhome_apt_notice` / `applyhome_apt_model` instead of the API, returning rows with the API's uppercase field names (columns first, then keys from the `extra` JSON). Only the condition keys the app uses are supported (`HOUSE_SECD/HOUSE_DTL_SECD::EQ`, `RCRIT_PBLANC_DE::GTE/LTE/LT`, `HSSPLY_ADRES::LIKE`, `HOUSE_MANAGE_NO/PBLANC_NO::EQ`); unknown ones raise. Read-only for requests (the daily loader refreshes them); geocoding still uses VWorld. `APPLYHOME_SOURCE=api` restores API calls.

App tables (`server/db.py`) hold documents as LONGTEXT JSON strings (preserves key order/numbers): `analysis_snapshots`, `portfolio_samples`, `app_settings`, and the land-trade cache (`land_complete/pages/errors`). Table/column names must stay stable (existing data). `MySqlLandStore` (`features/land_store_mysql.py`) subclasses `domain/land_store.LandStore` (SQLite) and keeps its interface/cache policy so `Collector` is unchanged. Bundled read-only samples come from `data/samples/` (`default.json` names the default). `V6.html` is no longer written to disk; `features/pages.py` renders it per request.

### Services worth knowing

- `SnapshotService.recompute` never trusts client-computed results: it re-runs `validate_snapshot` + `export_snapshot`, and rejects any payload containing a configured secret.
- `PortfolioService` samples are frozen captures (`persistencePolicy=portfolio_frozen_v1`); reading one must not recompute it with the current engine. The default sample is an explicit pointer and is never silently replaced.
- The dashboard page is ~19MB (template + default sample embedded in `__PF_SNAPSHOT__` and again in `__PF_PORTFOLIO__`). Rendering it per request made 20 concurrent loads peak ~1.6GB and got the process OOM-killed on a small EC2 ("connection refused"). `pages.PageCache` (on `app.state.page_cache`) renders it once, checks secrets once (`web.checked_bytes`), keeps a gzip copy, and serves it via `web.cached_html`; it rebuilds only when `PortfolioService.version()` (sorted sample ids+captured_at, plus the default-sample setting) changes. `PortfolioService.entries()` is cached on the same id list (samples are immutable and there is no delete); callers must not mutate the returned items. `default_id()` validates against `entries()` instead of re-reading. Every saved sample is still embedded in the page, so the page grows with the number of samples.
- `PublicData.slot()` allows at most 4 concurrent upstream lookups through `domain.public_api.Collector` (429 `BUSY` otherwise).

### Trained model

`features/model.py` defines the `Predictor` protocol and `ModelHolder`, which loads `MODEL_ENTRYPOINT=module:Class` from `MODEL_DIR` (`./data/models`, mounted read-only). With no entrypoint the app starts normally, `/api/model/status` reports `not_configured`, and `/api/model/predict` returns 503 `MODEL_NOT_READY`. Model failures at load never block startup. Details in `data/models/README.md`. The analysis engine does not depend on the model.

The current model is the teammate's **LinearRegression** (`data/models/land_price_linear.py`, `MODEL_ENTRYPOINT=land_price_linear:LandPriceLinearPredictor`; files `data/models/linear/model.joblib` (~65KB, tracked, plain git) + `linear/model_info.json`, kept under the teammate's names). It subclasses `LandPricePredictor` and overrides only `load` and `_predict_log1p` (+ `_warnings`): the joblib is a dict `{format_version: 1, pipeline, config, model_info}`; pipeline = ColumnTransformer(StandardScaler on the 12 numbers, OneHotEncoder(drop='first', handle_unknown='ignore') on `land_group_key`) → TransformedTargetRegressor(log1p/expm1, LinearRegression). `_predict_log1p` runs preprocess + inner regressor (1-row pandas DataFrame, columns by name) and the base class does expm1 + clip at 0, so prices equal `pipeline.predict` (tested). `load` refuses on feature-list mismatch, on a `model_info.json` whose `split_fingerprints` differ from the bundle's, and on sklearn `InconsistentVersionWarning` (needs `scikit-learn==1.9.1`, Python ≥3.11, pandas). Unknown groups (one-hot all zero) are flagged via `knownGroup`/warning (sklearn's unknown-category UserWarning is filtered); out-of-range = beyond scaler mean ± 4σ. Version = sha256[:12] of the joblib. Same inputs/groups/split as CatBoost; on the latest month linear/CatBoost unit price ratio median ≈1.17 (p5 0.51, p95 2.33). The previous model, the teammate's CatBoost #23 (handoff package `개발자전달_CatBoost23_20261027`): `data/models/land_price_model.py` (`MODEL_ENTRYPOINT=land_price_model:LandPricePredictor`) loads `model.cbm` (~110MB, git-ignored, copied by hand; `catboost==1.2.10`) and the tracked `model_info.json` (features, 5,085 `training_groups`, log1p target); `load` refuses if code/info/model feature lists differ. It predicts the 6-months-ahead monthly median unit price (KRW/m², `expm1`, clipped at 0) of a group `"sgg|jimok_group|zone_group"` (jimok 대/전/답/임야/공장용지 else 기타; zone via the teammate's exact raw-name table `ZONE_TABLE` into 8 groups incl. 비도시지역 and `용도미지정 등`; unknown raw zone names raise, never guessed). `data/models/land_price_inputs.py` builds the 12 numeric inputs from tracked `data/models/inputs/` (group monthly history, region map, regional macro, COFIX release history; regenerated from a handoff package with `inputs/make_inputs.py`, pandas+pyarrow only there) using the teammate's `tools/build_context.py` rules: feature month = forecast month − 2, target = +6, COFIX = latest released by forecast-month end, exact-month joins only — no imputation; missing → `InputsMissing` → `LookupError` → 409 `MODEL_DATA_MISSING`. Latest forecast month is limited by macro (to 2026-07) and COFIX releases (to 2026-08) → 2026-08; `build_latest` looks back up to 6 forecast months per group, so target months can differ per group (shown to users). Verified: 6,000 teammate samples match all 12 features; the 5 example predictions match. `POST /api/model/land-estimate` (in `features/model.py`) prices parcels (pnu[:5] = sgg, raw jimok, raw zone, area) per group and returns rows + `totalWon` (only if all priced) / `partialWon`. **The model now sets the land purchase amount used everywhere.** `analyze(inputs, partial, land_model=None)` / `validate_snapshot(..., land_model)` / `persistence.export_snapshot(..., land_model)` take `land_model` = `ModelHolder.estimator()` (= `ModelHolder.land_estimate`, or None when the model isn't ready); `/api/analyze`, `SnapshotService` and `PortfolioService` pass it (domain never imports features). `domain/analysis/land_price._apply_land_model` (run right after `_land`, before `_apply_finance_price`) sets `land.representativeWon` = Σ(model unit × area for priced parcels) + (area-weighted average model unit × area of unpriced/unclassifiable parcels) × landAdjustmentPct factor — the user chose 'fill with model average'. It keeps `comparablesRepresentativeWon`, sets `amountBasis` ('model'|'comparables') and `modelEstimate` (rows with `basis` 모델 예측/평균 단가로 채움, counts, average, targetMonths). Falls back to comparables when the model is off, raises, prices no parcel, or a parcel has no area. ## 수지분석 (budget) 계산식

User request 2026-10-29 (Gangnam-type sites: land is so large that the old "target margin 15% → allowable spend → 지출% shares" setup could not work). The target margin is no longer an input and has no default; it is a result: `targetMarginPct = (총수입 ÷ 총지출 × 100) − 100` (user request 2026-10-30, second change the same day; first was (총수입 − 총지출) ÷ 총수입 × 100, then briefly 총수입 ÷ 총지출 × 100; 0% = break-even, negative = loss; console colors: <0 red, <10 yellow, else green). The 독립 예상비용 `_costs.marginPct` (profit ÷ income) is a separate figure and was not changed. Defaults (`costs.EXPENSE_DEFAULTS` = `revision-model.FINANCE_DEFAULTS.expenses`): 허용 공사비 = 계획 공급면적 (`development.supplyAreaM2`, the same assigned area revenue uses) ÷ 3.3 × 1,000만원 (`areaUnit`, value in 만원/평, construction only); 간접 7%, 분양제 6%, 제세공과금 5%, 금융 6.5% of 공사비 (`constructionPct`); 신탁 1% of 총수입 (`revenuePct`, `budgetAllocation.trustRatePct`). Other modes stay selectable: `budgetPct` (지출% = share of 총지출, solved as T = fixed ÷ (1 − Σ지출%), with 공사비% rows folded in when 공사비 itself is 지출%), `revenuePct`, `amount`. Server `costs._expense_priority_basis`/`_budget_allocation(inputs, revenue, land, errors, development)` and browser `budget-priority.expensePriorityBasis`/`revision-model.calculateBudget(input, revenue, land, supplyM2)` are the same algorithm; shared examples in `frontend/test-budget-priority-fixtures.json` are checked by `frontend/test-budget-priority.mjs` and `tests/test_budget_parity.py`. When inputs are incomplete, rows that don't depend on others still show amounts. Old inputs: `assumptions.targetMarginPct` and `budgetAllocation.constructionPct/indirectPct/...` are ignored (explicit `financeEditor.expenses` edits are kept); `currentBudget(input, results)` recomputes a saved budget without `totalExpenseWon` (pre-change frozen samples) for display. The UI removed the '요청 목표 수익률' slider and shows the computed margin. '공사비%' is not offered in the 기준 dropdown (user request 2026-10-29: not a sensible reporting basis): rows still on the construction-based default (`constructionPct`, internal only) are shown as '지출%' with value = amount ÷ 총지출 × 100 (rounded to 0.01, tooltip names the 공사비 basis); typing or sliding turns that row into a real `budgetPct` (`V3Workbench.FinanceRow` `fromConstruction`/`shownMode`); the 독립 예상비용 section (`_costs`) still uses `targetMarginPct` only if a saved input has one. ## Configuration

All config is environment variables (see `.env.example`); in Docker they come from `.env` via compose, with `python -m server` from `env.load_environment`. That loader rejects unknown names, so any new variable must be added to `env.APP_NAMES`. `server/settings.py` reads them. VWorld keys must match `VWORLD_DOMAIN`.
